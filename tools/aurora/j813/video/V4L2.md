# Native M5 AVE through V4L2

The experimental AVE module exposes a standard memory-to-memory video device
named `Apple M5 AVE H.264`. Its raw OUTPUT queue accepts 320x240 NV12; the
CAPTURE queue returns H.264 produced by the M5 firmware. Both queues use
standard V4L2 MMAP buffers. The kernel copies input into its owned DMA arena,
runs the captured Open/Start/Process/Complete/Stop/Close sequence, and copies
the firmware parameter sets and IDR slice into the capture buffer.

This is the fixed-profile foundation for general application integration.
It advertises only 320x240 at 1 fps and produces a new all-IDR session for
each frame. Resolution, bitrate, frame-rate and GOP controls are not yet
generalized. GPU rendering, sustained 1080p/4K throughput, power consumption,
HEVC and streaming require separate qualification.

## Build and setup

`build-m5-v4l2.sh` runs in the existing J813 Linux builder. It creates a
separate v8 kernel, media modules, AVE module and initramfs in
`artifacts/video/v4l2`. The qualified v7 payload is preserved. VIM2M selects
the hidden media dependencies during this out-of-tree build; its virtual
test driver must not be loaded on the M5. `boot-linux.py --video-v4l2` selects
the candidate and retains the existing M5 firmware and MTP preflight.

Before starting firmware, load `apple_ave` and run `/bin/m5-v4l2-probe`.
This real ioctl test checks the card identity, exclusive open, both format
queues, frame interval, allocation, mapping, busy-format rejection and
reopening. It does not start streaming or issue encoding commands.

Firmware setup remains privileged and experimental. Start firmware once,
send Config, and generate `start` and first-frame `process` templates with
`ave-relocate-avc.py` using this boot's measured arena address and size.
Store them as `/lib/firmware/apple/ave/m5-start.bin` and `m5-process.bin`.
The private captured templates and firmware are not distributed here.
Write `1` to `ave-v4l2-enable` in the AVE debugfs directory to validate their
sizes, plane geometry and boot-local surface addresses. A successful enable
gives the V4L2 engine exclusive ownership; raw command, poll and arena writes
then return `EBUSY`. Only one application may open the encoder at a time.

The driver keeps firmware, power and DMA resources pinned until reboot.
Never unload it after firmware startup, resume a failed firmware command,
reuse templates from a previous boot, or run another raw AVE writer.
The original debugfs-only module build remains available on kernels without
the V4L2 media dependencies.

## FFmpeg test

Use the distribution's FFmpeg with its existing `h264_v4l2m2m` encoder:

```sh
ffmpeg -f rawvideo -pixel_format nv12 -video_size 320x240 -framerate 1 \
  -i input.nv12 -an -c:v h264_v4l2m2m -g 1 -bf 0 -f h264 elementary.h264
ffmpeg -r 1 -i elementary.h264 -c:v copy recording.mkv
```

Direct MPEG-TS also works and preserves the input timestamps:

```sh
ffmpeg -f rawvideo -pixel_format nv12 -video_size 320x240 -framerate 1 \
  -i input.nv12 -an -c:v h264_v4l2m2m -g 1 -bf 0 \
  -f mpegts -muxdelay 0 -muxpreload 0 recording.ts
```

On the minimal RAM desktop, give the existing `video` group access to the
device (`chgrp video /dev/video0; chmod 660 /dev/video0` inside the desktop).
The `aurora` user is already in that group. It needs no debugfs access.
The node permissions must be restored after recreating the device.
`run-v4l2-test.sh INPUT NEW_RESULT_DIR mpegts aurora` checks that user path;
the default mode is raw H.264 followed by a Matroska remux.

There is no custom FFmpeg codec or userspace broker in this path. Save
`ave-status` before and after the invocation, its exit status and application
log, the original input, and the MKV. `validate-v4l2.py` checks the firmware
command/frame deltas, CPU-decodes every frame, compares pixels and timestamps,
and writes a portable result. Driver registration and a successful build
alone do not establish a working encoder; consult the hardware result record.

The profile currently supplies SPS/PPS in-band with each frame. A direct
Matroska output attempt failed at header creation before encoding began.
The second command above copies the encoded stream into a container and
constructs timestamps at the supplied frame rate; it does not re-encode video.

## Hardware qualification

On 2026-09-10, stock FFmpeg 8.0.1 encoded two ten-frame clips on native
M5/J813 Linux v8. The raw/remux clip ran as root; the direct MPEG-TS clip ran
as `aurora`. Both independently decoded all ten frames at 50.8–53.1 dB PSNR,
with correct ordering and one-second timestamps. Each used 60 firmware
commands and replies with zero failures. Mean kernel transaction time was
41.2–41.3 ms per frame across these short, offline runs; this is not a
sustained-throughput or power measurement. The direct MPEG-TS test did not
reconstruct timestamps through a second remux operation.

The ioctl probe also passed format negotiation, MMAP buffers, exclusive
open and close/reopen before firmware startup. A Linux 7.1 API difference
requires callbacks to obtain their context from `file_to_v4l2_fh(file)`;
the legacy ioctl `priv` argument is NULL. The native probe exercises this.

## OBS built-in FFmpeg output

OBS 32.1's Advanced output mode can use `RecType=FFmpeg`,
`FFVEncoder=h264_v4l2m2m`, `FFFormat=mpegts` and `FFExtension=ts` for a local
recording. Use 320x240 NV12 at 1 fps, GOP 1 and `bf=0`. The bitrate setting
does not control the captured profile and is not qualified. This route uses
OBS's distribution-provided `ffmpeg_output`; it needs no custom encoder or
root broker. The original experimental `m5_ave_h264` adapter is retained as
a separate historical path and must not run against an owned V4L2 device.

For a bounded synthetic test, install `obs-studio libobs-dev gcc libc6-dev
wmctrl`, copy `obs/setup-test-profile.py`, `obs/fixture-v4l2.c` and
`obs/run-v4l2-test.sh` to `/desktop/tmp/m5-obs`, then invoke the runner from
the initramfs with a new `m5-ave-obs-test...` profile name and
`m5-obs-v4l2-result...` result name. It records rotating color bars without
screen, microphone or network streaming capture. The fixture registers no
encoder; it removes its temporary scene and waits for deferred destruction
before requesting a normal window close. The runner requires application
exit 0. An earlier version left dynamic sources until global teardown and
crashed intermittently after recording; those runs are not clean-exit proof.

`obs/validate-v4l2.py` verifies the selected stock codec, ordinary user,
OBS's live video-device file descriptor, firmware command/frame deltas,
CPU decoding, timestamps, animated bar phases and clean exit. This scene
check is distinct from the exact-input YUV PSNR checks in the FFmpeg test;
RGB colorimetry of the captured SPS is not yet qualified. OBS compositing
still uses llvmpipe, independently of AVE hardware encoding.

The interface follows the Linux [stateful encoder API](https://docs.kernel.org/userspace-api/media/v4l/dev-encoder.html)
and [memory-to-memory helpers](https://docs.kernel.org/driver-api/media/v4l2-mem2mem.html).
