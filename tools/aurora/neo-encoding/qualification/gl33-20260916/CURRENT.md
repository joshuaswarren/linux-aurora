## 2026-09-13 late: depth-wrap family recovered (36/36) -- register-LOD texel fetch root cause

**Root cause (hardware-proven):** every fragment `texelFetch` with a non-constant LOD returned exact zeros on G17P although the emitted COPY / PACK_SMPIR / pixel gate / SMP bytes matched Apple's `t.read(uint2(uv), uint(lod))` fragment witness field-for-field (decode-greedy, `native-txf-variants/varying`). capture_vertex_interleaved, diagnosed. A standalone oracle now reproduces the conformance program exactly (`asahi-g17p-gl-xfb-interleaved`: fifteen constant vec4 varyings plus a position chosen by gl_VertexID, captured interleaved with gl_Position last while the same draw renders to a one-channel float target). The conformance case reports only "Fail"; the oracle reports which check failed and where. It passes on llvmpipe, and on G17P it localises the failure precisely: points, lines, line loops and line strips all capture correctly, while all three triangle primitives lose exactly the z and w components of two captured varyings. The cause is spilling: the geometry copy program's three strip-copy blocks keep all sixty-five captured values live at once, the allocator exceeds the 192-half AGX3B budget, and the hardware program carries eighteen stack operations. G17P vertex-program spilling is already known unreliable, so this reduces to that open problem rather than a transform feedback bug. KHR-GL30.transform_feedback.discard_vertex is the same shader: its conformance class inherits CaptureVertexInterleaved.

Found and fixed along the way: a device store has no destination, so the scoreboard never tracked the registers it reads, and a later redefinition could race the outstanding store. Stores now hold their payload registers until they retire. Loads keep latching their address at issue, which a native witness requires. This did not change the interleaved capture result, so it is a latent hazard fix rather than the cause. `framebuffer_blit.multisampled_to_singlesampled_blit_color_config_test` (commit ef5bcf36dbd). The root cause was that G17P addresses each tilebuffer sample explicitly and the Gallium fragment epilog never got `agx_nir_lower_g17p_tile_samples`, which the Vulkan driver has applied all along. Every multisample draw reached only sample zero, so a four-sample resolve produced a quarter of the drawn colour. A new oracle, `asahi-g17p-gl-msaa-resolve`, separates the draw from the resolve by reading each sample back with texelFetch first; before the fix it reports samples one to three untouched and a resolved pixel of 64 where 255 was drawn. Two follow-on gates then had to move: multisample tile layouts are now admitted by physical format rather than an ad-hoc API-format list (a four-sample sweep of the oracle covers rgba8, rgb565, rgba4, rgb5_a1, rgb10_a2, r8, rg8, r16f and rgba16f; sRGB and packed float are covered by the conformance blit itself), and the background program size guard scales with the sample count because the per-sample lowering repeats the body once per sample, making a four-sample reload 990 bytes against a 512-byte guard.

The depth blit is a different problem than its name suggests. Its trace shows the depth values blitting correctly and the failure is `expected STENCIL[1] but got STENCIL[0]`: the stencil half of a depth-stencil blit from a multisample source is lost. The driver already lowers a stencil-plane blit to an R8_UINT colour blit for G17P (`agx_g17p_stencil_plane_blit_shape` in agx_blit.c), so the open question is whether that lowering handles a multisample source.

Tooling note: `fast-iteration.py` asserts its candidate filename matches `libgallium-[a-z0-9-]+\.so`, so an uppercase letter in the name makes the install fail silently and the next case runs against the previously installed driver. `scratchpad/install-candidate.sh` now installs and verifies the digest before any measurement.

ROOT CAUSE for the interleaved capture pair, found by reading the scratch plumbing rather than the packer. `agx_pipe.c` allocates vertex scratch and sets `c->vertex_helper.binary = agx_helper_program(...)`, and on G17P that returns zero: `asahi_clc.c`'s `target_supports_program()` does not qualify `libagx_helper` for the g17p target, so `libagx_g17p[LIBAGX_HELPER]` is NULL and `test-g17p-precompiled-fill.c` asserts that it is. The scratch region therefore has no servicing program and every spilled reload reads back zero, with no refusal anywhere. That is exactly the shape of the failure: the copy program carries 18 stack operations and loses precisely the components those reloads feed. Both `capture_vertex_interleaved` and `discard_vertex` ride on it, since the conformance class of the latter inherits the former.

Qualifying the helper is not a one-liner: with `libagx_helper` added to the g17p list, `asahi_clc` aborts at `agx_register_allocate.c:1752` on `(remat || ctx->key->has_scratch)`. The spill helper may not itself spill, and it does not fit the AGX3B 192-half register domain. Making it fit, or giving it a rematerialization-only allocation, is the next piece of work. The experiment was reverted so the tree builds.

The depth-stencil blit is blocked on a second, unrelated gap: the fragment program for a multisample stencil resolve reaches `agx_fast_link` with a nonzero shaded sample count, and that external sample loop is AGX2 machine code with no AGX3 form. `agx_nir_lower_tilebuffer`'s `dim_for_rt` sets `uses_sample_shading` whenever the target is multisample, because it indexes the tilebuffer image by gl_SampleID. The stencil resolve now correctly takes sample zero (commit 56a3f460686), which is the right semantics either way, but the link still fails. Encoding a G17P sample loop, or folding it in NIR, would also unblock any application using per-sample shading, so it is worth doing properly rather than working around.
